# Идемпотентность в HTTP API

## Простыми словами

**Идемпотентная операция** — это операция, повторный вызов которой дает тот же результат на сервере, что и один вызов. Неважно, отправили вы запрос один раз или десять: итоговое состояние данных будет одинаковым.

Пример из жизни: кнопка вызова лифта. Нажмете один раз или пять, лифт приедет один. А кнопка «добавить в корзину» неидемпотентна: каждое нажатие может добавить еще один товар.

## Зачем это нужно

Сеть ненадежна. Типичная ситуация:

1. Клиент отправляет запрос на оплату.
2. Сервер обрабатывает его и списывает деньги.
3. Ответ теряется из-за обрыва связи или таймаута.
4. Клиент не знает, что произошло, и отправляет запрос повторно.

Если операция идемпотентна, повтор безопасен. Если нет, пользователя могут дважды списать деньги или создать два одинаковых заказа.

## Какие HTTP-методы идемпотентны

| Метод | Идемпотентен | Комментарий |
|---|---|---|
| `GET` | да | Только читает данные |
| `HEAD`, `OPTIONS` | да | Не меняют состояние |
| `PUT` | да | Полностью заменяет ресурс заданным содержимым |
| `DELETE` | да | После первого удаления ресурса уже нет, повторы ничего не меняют |
| `POST` | **нет** | Обычно создает новый ресурс при каждом вызове |
| `PATCH` | **зависит от реализации** | `{"name": "Анна"}` идемпотентно, а «увеличить счетчик на 1» нет |

## Примеры

**Идемпотентно:**
```http
PUT /users/42
{"name": "Анна", "email": "anna@example.com"}
```
Сколько бы раз вы это ни отправили, пользователь 42 будет с этими данными.

**Неидемпотентно:**
```http
POST /orders
{"product_id": 7, "quantity": 1}
```
Каждый вызов создаст новый заказ, и в итоге их будет несколько.

## Важные нюансы

- **Идемпотентность касается состояния сервера, а не ответа.** Первый `DELETE /users/42` вернет `204`, а второй может вернуть `404`. Ответы разные, но состояние одинаковое: пользователя нет.
- **Идемпотентность не равна безопасности.** «Безопасные» методы (`GET`, `HEAD`, `OPTIONS`) вообще не меняют данные. `PUT` и `DELETE` идемпотентны, но данные меняют.
- **Это соглашение, а не гарантия.** Если разработчик реализовал `GET` с побочными эффектами, например удалением записи, протокол ему не помешает. Но так делать нельзя: клиенты, прокси и кеши рассчитывают на стандартную семантику.

## Как сделать `POST` идемпотентным

Для критичных операций, таких как платежи и заказы, используют **ключ идемпотентности** (`Idempotency-Key`):

```http
POST /payments
Idempotency-Key: 8f14e45f-ceea-4b7c-9d2a-1a2b3c4d5e6f
{"amount": 1000, "currency": "RUB"}
```

Как это работает:

1. Клиент генерирует уникальный ключ, обычно UUID, и отправляет его в заголовке.
2. Сервер при первом запросе выполняет операцию и сохраняет результат вместе с ключом.
3. Если приходит повторный запрос с тем же ключом, сервер **не выполняет операцию заново**, а возвращает сохраненный результат.

Такой подход используют Stripe, PayPal и многие другие платежные API.

## Что запомнить

- Идемпотентность значит, что повтор запроса не меняет итог.
- `GET`, `PUT`, `DELETE` идемпотентны, `POST` нет.
- Это важно из-за ретраев и сетевых сбоев.
- Для `POST` с важными действиями используйте `Idempotency-Key`.
- Проектируя свой API, выбирайте метод с учетом этих свойств. Например, «установить статус заказа в `paid`» лучше делать через `PUT` или `PATCH`, а не через операцию «переключить статус».
