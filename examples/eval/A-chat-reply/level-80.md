Идемпотентность — свойство запроса. Если отправить его один раз или десять раз подряд, состояние сервера будет одинаковым. Повтор не создаёт новых побочных эффектов.

Например, `PUT /users/42` с телом `{"name": "Анна"}` задаёт пользователю имя. После первого запроса имя «Анна», после десятого тоже «Анна». А `POST /orders` создаёт заказ, и десять таких запросов создадут десять заказов.

Свойство нужно из-за ненадёжной сети. Клиент отправил запрос и не получил ответ из-за тайм-аута. Он не знает, дошёл запрос до сервера или нет. Если метод идемпотентный, клиент повторяет запрос без риска. Если нет, повтор может дважды списать деньги или создать дубль заказа.

Спецификация HTTP (RFC 9110) определяет такие методы как идемпотентные:

- GET
- HEAD
- OPTIONS
- PUT
- DELETE

POST и PATCH идемпотентность не гарантируют. PATCH с телом `{"name": "Анна"}` даст одинаковый результат при повторе, а PATCH с операцией «увеличить счётчик на 1» нет.

Идемпотентность и безопасность — разные свойства. Безопасный метод ничего не меняет на сервере: GET, HEAD, OPTIONS. DELETE идемпотентен, но небезопасен, потому что удаляет данные. Идемпотентность описывает состояние сервера, а ответы могут отличаться. Первый `DELETE /users/42` вернёт 204, второй вернёт 404. Состояние при этом одно и то же: пользователя нет.

Чтобы сделать идемпотентным POST, многие API принимают заголовок `Idempotency-Key`. Клиент генерирует уникальное значение, например UUID, и отправляет его с запросом:

```
POST /payments
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
```

Сервер запоминает ключ и результат первого запроса. При повторе с тем же ключом он возвращает сохранённый результат и не создаёт платёж второй раз. Так работает, например, Stripe. Этот заголовок не входит в стандарт HTTP, поэтому проверьте в документации конкретного API, поддерживает ли он ключи идемпотентности.
