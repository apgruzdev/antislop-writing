Запрос идемпотентен, если десять повторов дают то же состояние сервера, что и один. Состояние сервера — это данные, которые он хранит: записи в базе, файлы, счета. Ответы на повторы могут отличаться: идемпотентность касается только состояния сервера. Первый `DELETE /users/42` вернёт 204, второй вернёт 404. Пользователя после обоих запросов нет, поэтому `DELETE` идемпотентен.

Идемпотентность нужна из-за сбоев сети. Клиент отправил запрос, но время ожидания ответа истекло. Клиент не знает, выполнил ли сервер запрос. Идемпотентный запрос клиент повторяет без риска. Повтор неидемпотентного запроса может выполнить действие дважды, например списать деньги второй раз.

Стандарт HTTP (RFC 9110) относит к идемпотентным методы GET, HEAD, OPTIONS, TRACE, PUT и DELETE. `POST` идемпотентным не считается. `PATCH` тоже не гарантирует идемпотентность.

```
PUT /users/42
{"name": "Anna"}

POST /orders
{"item": "book"}
```

`PUT` задаёт итоговое значение: после любого числа повторов имя пользователя равно Anna. `POST` создаёт новую запись: десять повторов создают десять заказов.

Стандарт требует идемпотентность от сервера, но не проверяет её. Допустим, `DELETE /queue/first` удаляет первый элемент очереди. Тогда каждый вызов удаляет новый элемент, и метод не идемпотентен. Проверьте поведение метода в документации API.

Чтобы безопасно повторять `POST`, API вводят ключ идемпотентности. Клиент создаёт уникальную строку и отправляет её в HTTP-заголовке, например `Idempotency-Key`. Сервер запоминает ключ и результат. Повтор с тем же ключом возвращает сохранённый результат и не создаёт новый заказ. Так работает платёжный API Stripe. Имя заголовка и срок хранения ключа задаёт конкретный API.
